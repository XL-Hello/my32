# 首页卡住问题分析报告

> 主题：ESP32-S3 + LVGL8 + ILI9341（SPI2）系统在启动后约 4 秒 UI 永久卡死的问题。
> 结论：SPI 完成回调链未 IRAM 化，在 Wi-Fi/NVS 的 flash 缓存禁用窗口内卡住 SPI ISR，导致 SPI 总线锁 BG 位残留、`spi_device_acquire_bus` 永久阻塞。将整条完成回调链 IRAM 化后修复。

---

## 1. 现象

- 芯片：ESP32-S3，ILI9341 经 SPI2（`SPI2_HOST`）驱动，HR2046 触摸经 SPI3 驱动。
- 故障：启动后首页渲染成功约 1.5 秒（约 3.5s 首次温湿度刷新触发重绘时），UI **永久卡死、从不恢复**。
- 卡死期间：
  - Wi-Fi 连接、SNTP 同步、RGB LED、WS2812B 等**独立任务照常运行**；
  - 温湿度、时钟等由 LVGL 定时器驱动的刷新**全部停止**；
  - 无看门狗复位、无异常崩溃日志。
- 触发条件（实测组合）：

  | 绘图缓冲 | SPI 时钟 | 结果 |
  | --- | --- | --- |
  | PSRAM | 10 MHz | 卡死 |
  | 内部 DMA | 40 MHz | 卡死 |
  | 内部 DMA | 10 MHz | 正常 |
  | 内部 DMA | 40 MHz + IRAM 回调链 | 正常（本报告修复） |

- **Heisenbug 现象**：在正常路径（每帧刷新）中打印日志后，卡死反而消失；日志本身改变了时序与缓存行为，掩盖了问题。

## 2. 分析过程

### 2.1 定位"阻塞点在 LCD SPI 提交链路"

- 修复了 `pdMS_TO_TICKS(1)` 向下取整为 0 导致的空转问题后，卡死依旧。
- 通过 `disp_disable_update()` 旁路 LCD 刷新，温湿度日志持续输出 → 证明 LVGL/UI 定时器本身健康，**阻塞点 100% 在 LCD SPI 刷新提交链路**。

### 2.2 诊断方法（遵循"正常静默、异常才打印"原则）

关键教训：正常路径打日志会改变时序（每帧一条 `log_info` 约 9.6 ms UART 阻塞），掩盖竞态。因此诊断改造遵循：

- **正常路径静默**：仅用内存变量记录阶段/计数，不打日志；
- **异常才打印**：仅在卡死（stall 检测）、错误、慢阶段（>100 ms）时输出。

落地的诊断手段：

1. **应用层分段追踪**：`lcd_draw_bitmap` 内把 `esp_lcd_panel_draw_bitmap` 展开为 `CASET / RASET / COLOR` 三段，用 `esp_timer` 打点并记录当前阶段与"已提交未完成"计数（`inflight`，ISR 回调中递减）。
2. **SDK 层子阶段追踪**：在 `esp_lcd_panel_io_spi.c` 的 `tx_param`/`tx_color` 内记录 `acq / drain / poll / queue` 子阶段（内存态），供 stall 诊断读取。
3. **stall 告警增强**：`lvgl_port` 的 stall 诊断在卡死时打印当前 LCD 阶段、在飞计数、SPI 子阶段、内部堆余量。

### 2.3 关键诊断结果

静默固件（内部 DMA + 40 MHz）稳定复现，stall 告警为：

```
W (4007) lvgl: UI thread stalled for 540 ms at lv_timer_handler
  (heap_internal=139252 B, lcd_phase=CASET inflight=0 spi_sub=acq)
```

判读：

- `lcd_phase=CASET`：卡在 `lcd_draw_bitmap` 的 CASET 阶段，即 `esp_lcd_panel_io_tx_param(0x2A)` 内部；
- `spi_sub=acq`：确凿卡在 **`spi_device_acquire_bus(portMAX_DELAY)`**（非 drain/poll/queue）；
- `inflight=0`：上一笔 DMA 已完成、ISR 完成回调已执行，排除"排空等上一笔未完成"；
- 堆余量充足（139 KB），排除内存耗尽。

## 3. 根因

### 3.1 直接原因：SPI 总线锁 BG 位残留导致 `acquire_bus` 永久阻塞

`spi_device_acquire_bus(portMAX_DELAY)` 内部（`spi_bus_lock_acquire_start` → `acquire_core`）：

- 若读取到的状态位含 **BG 位**（SPI ISR 正在处理）或 **LOCK 位**（总线被持有），则 `dev_wait(portMAX_DELAY)` **永久阻塞**等待被 resume；
- 一旦 SPI ISR（BG 处理器）卡住未退出，BG 位残留，之后所有 `acquire_bus` 全部永久阻塞 → UI 永久冻结。

### 3.2 深层原因：SPI ISR 在 flash 缓存禁用窗口内执行 flash 中的完成回调

- 项目开启 `CONFIG_SPI_MASTER_ISR_IN_IRAM=y`（SPI ISR 本身在 IRAM），但**完成回调链全在 flash**：
  ```
  SPI ISR
    → lcd_spi_post_trans_color_cb        (esp_lcd，flash)
      → lcd_color_trans_done_callback    (lcd.c，flash)
        → lcd_flush_ready_callback       (lv_port_disp.c，flash)
          → lv_disp_flush_ready          (LVGL，flash)
  ```
- Wi-Fi 连接阶段会频繁读写 NVS/flash，这些操作会**禁用共享 flash 缓存**。若 SPI ISR 恰在该窗口内调用 flash 中的回调，CPU 无法取指 → ISR 卡住 → 总线锁 BG 位残留。
- 40 MHz 下 SPI DMA/ISR 节奏更快，命中该窗口的概率显著升高；PSRAM 缓冲（每帧 19.2 KB 内部临时分配 + 拷贝）也会在 10 MHz 下制造类似时序抖动触发同一问题。这就是"内部 + 10 MHz 才稳定"的原因。

### 3.3 为什么加日志会"变正常"

每帧 `log_info` 输出约 9.6 ms 的 UART 阻塞，彻底改变了 ISR/任务的相对时序与缓存访问行为，把触发窗口避开，属于典型的 Heisenbug。

## 4. 优化方案（已实施：方案 C，IRAM 化回调链）

### 4.1 方案对比

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| A. 稳定基线 | 绘图缓冲保持内部 + SPI 10 MHz | 可用但刷新慢（全屏约 123 ms） |
| B. 经验提速 | 小步试 16/20 MHz | 未根治，仅规避 |
| **C. IRAM 化回调链（选定）** | 整条完成回调链放入 IRAM，数据放内部 DRAM | **根治，可稳定运行 40 MHz** |

### 4.2 改动内容

将下述完成回调链全部标记 `IRAM_ATTR`（`LV_ATTRIBUTE_FLUSH_READY = IRAM_ATTR`），并确保其访问的数据位于内部 DRAM：

| 环节 | 函数 | 位置 |
| --- | --- | --- |
| SPI driver post 回调 | `lcd_spi_post_trans_color_cb` | `esp-idf/components/esp_lcd/src/esp_lcd_panel_io_spi.c` |
| esp_lcd 回调 | `lcd_color_trans_done_callback` | `components/drivers/display/ili9341/lcd.c` |
| 用户回调 | `lcd_flush_ready_callback` | `components/adapters/lvgl_port/lv_port_disp.c` |
| LVGL | `lv_disp_flush_ready` / `lv_disp_flush_is_last` | `components/adapters/lvgl_port/lv_conf.h`（`LV_ATTRIBUTE_FLUSH_READY=IRAM_ATTR`） |

数据侧：`CONFIG_SPIRAM_USE_CAPS_ALLOC=y`（默认 `malloc/calloc` 走内部 DRAM），`panel_io` 结构与相关静态量均在内部 DRAM，满足 ISR 数据访问要求。

### 4.3 验证（按"符号地址实证"要求，非仅看源码）

- **链接器校验**：ESP-IDF 链接器会拦截 IRAM 函数引用 flash 符号的情况，编译全程无此类错误，说明链内调用均可 IRAM 执行。
- **nm 符号地址**（`.iram0.text` 区间 `0x40378404 ~ 0x4038DC0B`）：

  | 符号 | 地址 | 位置 |
  | --- | --- | --- |
  | `lcd_spi_post_trans_color_cb` | `0x40380f50` | IRAM ✓ |
  | `lcd_color_trans_done_callback` | `0x4037bc28` | IRAM ✓ |
  | `lcd_flush_ready_callback` | `0x4037bbfc` | IRAM ✓ |
  | `lv_disp_flush_ready` | `0x40380f38` | IRAM ✓ |

- **运行验证**：40 MHz + 内部缓冲，温湿度持续刷新至 33 s+（4 次），全程无 `stalled at lv_timer_handler`、无 `spi_sub=acq`、无 LCD 错误。

## 5. 遗留与后续建议

1. **`lcd_spi_pre_trans_cb`（SPI ISR 在事务开始时调用）仍在 flash**（地址 `0x42042524`），内部调用 `gpio_set_level`（flash）。本次修复针对完成链已足够；若要彻底 ISR IRAM 安全，可将其中 `gpio_set_level` 替换为 IRAM 安全的 GPIO 寄存器直写。
2. **诊断代码已全部清理**：`[DIAG]` 分段追踪、子阶段追踪、stall 告警以及 UI/DMA 阶段诊断基础设施均已移除；正常路径无任何额外日志，仅保留 LVGL 任务自身的 tick 与刷新逻辑。
3. 若后续希望提升刷新率，可在 IRAM 回调链基础上评估提高 SPI 时钟（当前 40 MHz）与减少大面积脏区重绘。
