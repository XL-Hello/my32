# 和风天气接入方案

## 1. 目标与范围

在首页顶部时间的右侧显示实时天气摘要：`天气图标 + 城市 + 温度`。首次启动默认城市为深圳（LocationID：`101280601`）；联网后可按第 3.3 节用公网 IP 推断坐标并反查城市。若定位不可用、用户未授权或结果不可信，则继续使用深圳。当前不做手动城市选择、预报页或天气详情页。

首页现有本地 AHT20 温湿度保持不变；天气摘要是互联网实时数据，二者不能混用。天气获取失败不影响首页、时钟、Wi-Fi 或传感器功能。

## 3. 数据与网络方案

### 3.1 API 请求

调用和风天气 API v7 的实时天气接口：

```text
GET https://<QWEATHER_API_HOST>/v7/weather/now?location=101280601&lang=zh
X-QW-Api-Key: <QWEATHER_API_KEY>
Accept-Encoding: identity
```

接口返回 `now.temp`、`now.icon`、`now.text`、`now.humidity`、`now.windSpeed` 和 `now.obsTime` 等字段；本期首页仅消费 `temp` 和 `icon`，但服务层保留其他字段，方便后续详情页复用。`location` 是实时天气接口的必填项，深圳的 LocationID 为 `101280601`。[和风天气实时天气接口](https://dev.qweather.com/docs/api/weather/weather-now/) [深圳 GeoAPI 示例](https://dev.qweather.com/en/docs/api/geoapi/top-city/)

`api_host` 必须使用控制台为该帐号分配的私有 API Host，不能写死已逐步停用的公共 Host。API v7 支持 API KEY 和 JWT；首期为降低 ESP32 端实现成本使用 `X-QW-Api-Key`，量产前应迁移 JWT，并在控制台收紧 API 与应用限制。[API Host 说明](https://dev.qweather.com/docs/configuration/api-host/) [认证与限制说明](https://dev.qweather.com/docs/configuration/authentication/)

和风天气响应通常使用 Gzip；本期请求显式声明 `Accept-Encoding: identity`，避免在 MCU 端引入解压路径。若服务端仍返回压缩内容，应在天气服务层增加流式 Gzip 解压，不能把压缩 JSON 传给解析器。[API 配置说明](https://dev.qweather.com/docs/configuration/api-config/)

### 3.2 与当前工程的衔接

当前 `wifi_manager` 会在确认互联网可用后启动 SNTP；天气服务应在该状态之后工作：

```text
Wi-Fi 已连接
    ↓
wifi_manager 状态 = WIFI_MANAGER_STATUS_INTERNET_READY
    ↓
weather_service 后台任务发起 HTTPS 请求（首次立即）
    ↓
解析并原子更新 weather_snapshot
    ↓
home_ui 的 1 s UI 定时器仅读取 snapshot 并刷新差异
```

HTTPS 使用项目既有 `esp_http_client` 和 `esp_crt_bundle_attach`。网络请求只能运行在独立 FreeRTOS 任务中，禁止放入 LVGL 定时器或 GUI 任务，避免界面掉帧。建议初始任务栈为 `6144 B`，HTTP 超时 `10 s`，刷新周期 `30 min`；失败后按 `1 min → 5 min → 15 min → 30 min` 指数退避。

### 3.3 公网 IP 定位与城市反查

用户提供的 `dreUI_msgService_getNetStatusLocRandom()` 是可行的“多源公网 IP 定位”策略：在多个服务间随机起始、失败切换，并兼容三种常见坐标字段：`latitude/longitude`、`lat/lon` 和 ipinfo 的 `loc`（`lat,lon`）。在 ESP-IDF 中应保留其容错语义，但**不能直接移植**以下桌面/嵌入式 Linux 写法：

- `system("curl ...")`、`/tmp`、`FILE` 临时文件：ESP-IDF 固件中没有 shell/curl，且无须将响应落盘；改为 `esp_http_client` 回调将有限大小（建议 `1024 B`）响应收集到 RAM。
- `http://ip-api.com/json/`：位置和公网 IP 属于敏感数据，生产固件不得回退到 HTTP；只接受 HTTPS 服务，TLS 使用 `esp_crt_bundle_attach`。
- `dreUI_logI(... data=%s)`：不得输出完整定位响应、IP、经纬度或精确城市；日志最多记录服务序号、错误类别与是否成功。
- `rand() % api_count`：先用 `esp_random()` 随机选起始服务；仅限数组长度为 2 时才能使用 `1 - first_idx`，通用实现应采用轮转索引 `(first_idx + k) % api_count`。

建议将定位做成单独的 `location_service`，每 24 h 最多查询一次，并仅在 Wi-Fi 状态为 `WIFI_MANAGER_STATUS_INTERNET_READY` 且用户明确开启“自动定位”时运行：

```text
HTTPS IP 定位服务 A（超时 8 s）
    └─失败→ HTTPS IP 定位服务 B（超时 8 s）
                ↓
          标准化为 lon,lat（经度在前）
                ↓
GET https://<QWEATHER_API_HOST>/geo/v2/city/lookup
    ?location=<lon>,<lat>&number=1&lang=en
    + X-QW-Api-Key / JWT
                ↓
保存 city_name、LocationID、lon、lat、定位时间至 NVS
                ↓
GET /v7/weather/now?location=<LocationID>&lang=zh
```

城市反查使用和风 GeoAPI `GET /geo/v2/city/lookup`；它支持 `lon,lat`，返回 `location[0].name`、`id`、`tz` 等字段。坐标传入时保留两位小数即可，且必须确认顺序是**经度,纬度**：用户给出的代码最终 `snprintf("%.4f,%.4f", lon, lat)` 的顺序正确。查询结果应要求业务 `code=200`、数组非空且 `id` 合法，再覆盖深圳默认值。[和风城市搜索 API](https://dev.qweather.com/docs/api/geoapi/city-lookup/)

城市名称应请求 `lang=en` 并以拉丁字符显示，例如 `Shenzhen`。这是因为现有 LittleFS 字体是预裁剪字体，无法保证已包含全球城市的中文字符；若必须显示中文名称，需在城市变化后下载/生成字体，或改为内置 Unicode 字库，二者都不适合本期。天气 `text` 未显示在首页，仍可请求 `lang=zh` 供后续页面使用。

定位结果的优先级为：**用户手动选择（未来） > 最近一次有效定位（NVS） > 本次自动定位 > 默认深圳**。公网 IP 定位只能到网络出口位置，精度不可承诺；不得用于安全、告警或精确地理围栏功能。设置页须提供“自动定位”开关、最近定位时间和“恢复深圳默认值”操作。

建议接口：

```c
typedef struct {
    bool valid;
    char city_name[32];       // 本期为英文，确保当前字体可显示
    char location_id[16];
    float longitude;
    float latitude;
    int64_t resolved_at_us;
} location_snapshot_t;

esp_err_t location_service_init(void);
esp_err_t location_service_refresh_if_due(void);
esp_err_t location_service_get_snapshot(location_snapshot_t *snapshot);
```

### 3.4 组件选择

用户提供的 `ningzixi/weather^1.1.0` 可作为 PoC 依赖候选：

```bash
source ./build.sh env
idf.py add-dependency "ningzixi/weather^1.1.0"
```

不过接入前必须核对该组件对 API v7、私有 API Host、`X-QW-Api-Key`/JWT、Gzip 及证书包的实际支持。它的示例将 `api_key`、`api_host` 和城市抽象在 `weather_config_t` 中，但本工程不应假设其仍符合当前 API 的认证约定。

推荐在 `components/services/weather/` 建立一个很薄的项目服务层：内部可先调用该组件；若其能力不匹配，则直接封装 `esp_http_client`。这样 UI 只依赖稳定的 `weather_service_get_snapshot()`，后续更换提供商或认证方式不会影响首页。

建议公开接口如下：

```c
typedef struct {
    bool valid;
    int8_t temperature_c;
    uint16_t icon_code;
    char text[16];
    char observed_at[32];
    int64_t updated_at_us;
} weather_snapshot_t;

esp_err_t weather_service_init(void);
esp_err_t weather_service_get_snapshot(weather_snapshot_t *snapshot);
```

## 4. 凭据与配置

不要把 API KEY、JWT 私钥或专属 Host 提交到源码、文档、LittleFS 镜像或串口日志。建议使用未纳入 Git 的 `sdkconfig.defaults.local` 或 CI 密钥注入生成下列 Kconfig 值：

```text
CONFIG_WEATHER_QWEATHER_HOST="<私有 Host>"
CONFIG_WEATHER_QWEATHER_API_KEY="<仅开发环境 API KEY>"
CONFIG_WEATHER_LOCATION_ID="101280601"
CONFIG_WEATHER_REFRESH_MINUTES=30
```

日志只输出 HTTP 状态、和风业务 `code` 与错误类型，严禁输出 `Authorization`、`X-QW-Api-Key`、完整 URL 中的敏感查询参数或响应中的任何凭据。和风天气要求使用 HTTPS；不得为调试关闭证书校验。[和风天气安全指南](https://dev.qweather.com/docs/best-practices/security-guidelines/)

## 5. 图标资源与映射

已生成 6 个 24×24、透明 RGBA、`currentColor` 单色源稿。SVG 供 UI 稿和后续编辑使用；同名 PNG 已放入实际打包目录 `app/ui/icon/png/`。

| 本地图标 | 覆盖的和风 `now.icon` | 用途 |
| --- | --- | --- |
| `weather-clear` | `100`、`150` | 晴 / 夜晴 |
| `weather-cloudy` | `101–103`、`151–153` | 多云 / 少云 |
| `weather-overcast` | `104`、`900`、`901`、`999` 及未知值 | 阴天或安全兜底 |
| `weather-rain` | `300–399` | 所有雨、阵雨、雷雨 |
| `weather-snow` | `400–499` | 所有雪、雨夹雪 |
| `weather-haze` | `500–515` | 雾、霾、沙尘 |

该映射刻意收敛为常用天气类型，未知新图标一律显示 `weather-overcast`，因此上游图标代码增加时不会导致 UI 空白。和风天气明确提示图标代码可能变化。[图标代码说明](https://dev.qweather.com/docs/resource/icons/)

运行时路径应在 `app/ui/icon/icon.h` 中新增为 `R:/littlefs/png/weather-*.png`；`home_ui.c` 使用 `ui_icon_set_src()` 装载。由于现有 `build.sh build flash` 会完整复制 `app/ui/icon/png/` 到 LittleFS `/png/`，无需修改打包脚本。

## 6. UI 状态与降级

| 状态 | 城市 | 温度 | 图标 | 进入条件 |
| --- | --- | --- | --- | --- |
| 加载中 | Shenzhen / 缓存城市 | `--` | `weather-overcast` | 首次联网但尚无结果。 |
| 正常 | 已解析城市 | 例如 `28°` | 根据 `now.icon` 映射 | API `code=200` 且字段解析成功。 |
| 暂时失败 | 最近一次成功城市 | 最近一次成功值 | 最近一次成功图标 | 失败且缓存未超过 24 h。 |
| 失效 | Shenzhen / 缓存城市 | `--` | `weather-overcast` | 无缓存或最后成功数据已超过 24 h。 |

每次成功结果写入 NVS（温度、图标代码、观测时间、保存时间），重启时先展示缓存，再等联网刷新。缓存只是改善离线体验，不得伪装成实时数据。

## 7. 实施顺序与验证点

1. 在和风控制台创建项目、获取私有 API Host 与凭据；先用开发机 `curl` 验证深圳接口、认证和 `code=200`。
2. 建立 `weather_service`，实现 HTTPS、超时、响应大小上限（建议 2 KiB）、JSON 字段校验、状态快照和退避。
3. 将天气图标路径宏加入 `icon.h`，在 `home_ui` 新增 W01 标签和图像对象，时间按 T01 移位。
4. 若后续加入中文状态文案，将其补入 `app/ui/front/list_raw.txt`；本期动态城市使用英文，无需为全球城市预置字形。
5. 运行 `./build.sh build` 验证固件编译；本次有 PNG 和字体字符变更，再运行：

   ```bash
   ./build.sh build flash && ./build.sh flash flash
   ```

6. 使用 `./build.sh monitor` 观察 `weather` 日志。成功验收：打印 HTTP 200、业务 `code=200`、温度与图标码；首页 W01 显示解析后的城市和温度，图标可读。断网验收：首页持续响应，显示缓存或 `--`，没有重复重启、内存泄漏或 LVGL 线程告警。

建议的无敏感数据日志：

```text
I (weather) refresh succeeded: location=101280601 temp=28 icon=101 obs=2026-08-15T10:00+08:00
W (weather) refresh failed: transport=ESP_ERR_HTTP_CONNECT business_code=-- retry_in=300s
```
